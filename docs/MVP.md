# Hypermetrics MVP

## Goal

The MVP is a CoinGlass-like Hyperliquid analytics API focused on indexed active wallets.

The first version should not try to represent every Hyperliquid wallet with perfect freshness. The realistic goal is to build a useful, fresh view over wallets discovered from the Hyperliquid leaderboard:

- Hyperliquid leaderboard
- manually tracked wallets
- wallets already known from previous refreshes

The product should be explicit internally that endpoints are powered by the indexed wallet universe.

## Core Data Flow

```txt
leaderboard poller
        |
leaderboard candidates
        |
validation scan
        |
manual wallet seeds
        |
        v
wallets
        |
        v
priority refresh queue
        |
        v
Hyperliquid clearinghouseState
        |
        v
wallet_accounts_current
wallet_positions_current
wallet_account_snapshots
wallet_position_snapshots
        |
        v
aggregates and API endpoints
```

## Data Sources

### Leaderboard

The Hyperliquid leaderboard is the initial seed for high-value wallet candidates.

Observed endpoint:

```txt
https://stats-data.hyperliquid.xyz/Mainnet/leaderboard
```

Use it to discover candidates that are likely to matter early:

- high account value
- high PnL
- high ROI
- high volume
- named or visible traders

The leaderboard is not enough by itself. It is performance-oriented, not a complete open-position feed. Every discovered address still needs a `clearinghouseState` validation refresh before it is promoted into the indexed wallet set.

Recommended polling cadence:

```txt
every 5-15 minutes
```

### clearinghouseState

`clearinghouseState` is the source of truth for a known wallet.

It provides:

- account value
- margin used
- withdrawable balance
- open positions
- signed position size
- entry price
- liquidation price
- leverage
- position value
- unrealized PnL

This call is rate limited and must be controlled by the refresh queue.

## Rate Limit Baseline

Hyperliquid public REST has an aggregate limit of:

```txt
1200 weight / minute / IP
```

`clearinghouseState` costs:

```txt
2 weight
```

The theoretical maximum is:

```txt
600 wallets / minute / IP
10 wallets / second / IP
```

Recommended production target:

```txt
6-8 wallets / second / IP
```

This leaves room for market metadata calls, retries, occasional bursts, and operational safety.

## MVP Endpoints

The MVP can support the public API surface in stages.

### Stage 1

- `GET /api/hyperliquid/user-position`
- served directly from `clearinghouseState` on cache miss
- cached into current tables

### Stage 2

- `GET /api/hyperliquid/position?symbol=...&current_page=...`
- served from `wallet_positions_current`
- limited to indexed wallets

### Stage 3

- `GET /api/hyperliquid/whale-position`
- served from current positions
- filter by `abs(position_value_usd) >= 1000000`

### Stage 4

- `GET /api/hyperliquid/whale-alert`
- generated by comparing position snapshots
- approximate at first, then improved with better refresh cadence and deduplication

### Stage 5

- `GET /api/hyperliquid/wallet/position-distribution`
- `GET /api/hyperliquid/wallet/pnl-distribution`
- position distribution is aggregated from current indexed wallets
- historical/PnL distributions can add periodic aggregate snapshots when required

### Stage 6

- `GET /api/hyperliquid/global-long-short-account-ratio/history`
- generated from interval snapshots by symbol

## Current Position Tables

`wallet_accounts_current` should store one row per wallet:

- `wallet_address`
- `account_value`
- `margin_used`
- `withdrawable`
- `last_refreshed_at`
- `source_updated_at`

`wallet_positions_current` should store one row per wallet and symbol:

- `wallet_address`
- `symbol`
- `position_size`
- `entry_price`
- `mark_price`
- `liq_price`
- `leverage`
- `margin_balance`
- `position_value_usd`
- `unrealized_pnl`
- `last_refreshed_at`

## Whale Detection

A whale should initially mean:

```txt
abs(position_value_usd) >= 1000000
```

Whale alerts are generated by comparing previous and current state:

- no position -> position: open
- position -> no position: close
- same sign and absolute size increases: increase
- same sign and absolute size decreases: decrease
- sign changes: flip

For CoinGlass compatibility, expose:

```txt
position_action = 1 for open/increase
position_action = 2 for close/decrease
```

Internally, keep the richer action type.

## Known MVP Limitations

The MVP will not have complete market coverage.

Expected limitations:

- inactive whales may be missed until discovered or manually seeded
- position changes can be detected late if a wallet has low refresh priority
- whale alerts can miss intermediate changes between two snapshots
- distributions and long/short ratios only represent indexed wallets
- historical data starts when Hypermetrics starts collecting snapshots

These are acceptable for the first version if the backend is designed to improve coverage over time.
